\section{Evaluation}
\label{sec:eval}

We ask four questions.
\begin{itemize}
  \item[\rqref{1}] Does the typed grammar reach more of \pg than a
    random-mutation generator in the same time: more valid statements, more
    covered lines and branches, more SQL features and plan shapes?
  \item[\rqref{2}] Which bugs does \tool find, and how precise is each oracle?
  \item[\rqref{3}] On real bugs put back into \pg, which configuration finds
    how many, and how fast?
  \item[\rqref{4}] What does the commit-directed LLM extension add, and what
    does it cost in tokens, money and repair rounds?
\end{itemize}

\subsection{Subject and Benchmark}
\label{sec:subjects}

All servers are built from one commit of \pg master, \texttt{26bd08fb} of
16~October~2026, with assertions on. For \rqref{3} we built a benchmark of
real bugs in the style of Magma~\cite{hazimeh2020magma}, but by reverting
fixes instead of porting bugs forward. We took every commit between
31~July and 16~October~2026 that:
\begin{enumerate}
  \item changes the optimiser, executor, parser, rewriter or SQL-callable
    functions, and says in its message that it fixes a bug, because RQ3 is
    about bugs that reach users through SQL;
  \item adds a regression test, because its SQL is our proof that the bug can
    be triggered;
  \item reverts cleanly on the base commit, alone and together with the
    others, and the server still builds.
\end{enumerate}
This gives 23 fixes. We build three kinds of server: the \emph{fixed} server
(the base), one \emph{solo} server per bug (the base with only that fix
reverted), and the \emph{injected} server (all 23 reverted), on which the
campaigns run. For each bug we wrote a self-contained proof of concept (PoC)
from its regression test and ran it on the fixed and the solo server
(Table~\ref{tab:bench}). Twenty bugs change the result of their PoC. The
other three change only the plan, or need an equality operator that returns
NULL for non-NULL inputs, which no built-in type has; they leave the
denominator. On the injected server every PoC shows the same symptom as on its
solo server, so no injected bug hides another.

\subsection{Configurations}
\label{sec:baselines}

Every configuration (\emph{arm}) uses the same server, schema, executor,
oracles, time budget and per-trial random seed; the arms differ only in the
generator and in what the generator can attach.
\begin{description}
  \item[\arm{Random}.] A mutation-based generator over the same schema that
    edits seed queries at the token level. It cannot attach metamorphic
    checks, because it has no derivation trees.
  \item[\arm{Grammar}.] Step 1 alone: the typed grammar with
    feature-guided corpus, no metamorphic checks, no plan guidance.
  \item[\arm{Grammar+Oracles}.] Steps 1--4: metamorphic checks (including
    the RLS and CERT checks) on half the queries, plan-shape guidance,
    feedback-weighted alternatives and literals from the data profile. In
    \rqref{1}, \arm{Grammar+Oracles, flat} is the same arm without the weights,
    which isolates their effect.
  \item[\arm{+LLM}.] \arm{Grammar+Oracles} plus the fragments, seeds and
    equivalence rewrites that passed the \gate. For \rqref{4} we also run
    \arm{+LLM fragments} and \arm{+LLM seeds} alone. The LLM never sees the 23
    benchmark fixes: the commit miner excludes them.
\end{description}
All arms run with the plan-variant oracle and, in RQ3, the cross-version
oracle, because these do not depend on the generator.

\subsection{Measurements}
\begin{description}
  \item[\rqref{1}.] Statement validity (the share of statements that run without
    error), line and branch coverage of the backend from gcov, distinct SQL
    features from a catalogue of 148 and distinct plan shapes, over time.
  \item[\rqref{2}.] Distinct bug candidates per oracle after signature
    de-duplication, and the verdict of each after triage: real, duplicate,
    false positive, not a bug, or flaky (Equation~\ref{eq:precision}); we give
    precision before and after fixing each false-positive class. CERT
    candidates are performance issues and are counted apart.
  \item[\rqref{3}.] For each benchmark bug and arm: the number of trials that
    found it and the median time to the first finding. A crash or assertion is
    attributed by its signature; a wrong result or error is attributed by
    replaying the failing test case on the fixed server and on every solo
    server: it belongs to bug $i$ if it fails on solo server $i$ and not on the
    fixed server.
  \item[\rqref{4}.] Share of commits whose proposal passes the gate, repair
    rounds needed, reasons for rejection, diff coverage gained, equivalence
    rewrites proposed and accepted, tokens and cost; and the
    \rqref{1}--\rqref{3} measures of the three LLM arms.
\end{description}

\subsection{Setup}
Each arm runs \num{5} trials of one hour on one worker each, four workers in
parallel, on \num{machine}. Following Klees et al.~\cite{klees2018evaluating},
and Arcuri and Briand~\cite{arcuri2011practical}, we report medians with
interquartile ranges and 95\% bootstrap confidence intervals, compare arms
with the two-sided Mann--Whitney U test, and give the Vargha--Delaney
$\hat{A}_{12}$ effect size~\cite{vargha2000a12}. Each coverage worker writes its gcov counters to its
own directory, so parallel trials do not mix coverage. The LLM is Claude Opus
5.5 with structured output and a cached system prompt of about 9{,}000 tokens.

\begin{observation}
\label{obs:sampling}
Testing a claimed equivalence on sampled queries is not enough: the false
identity \texttt{\{e\} IS TRUE} passed 109 sampled checks and failed on the
first probe value, NULL.
\end{observation}

\subsection{\rqref{2}: Bugs and Oracle Precision}
\label{sec:rq2}
\num{Table: candidates and verdicts per oracle (from the triage ledger).}

So far \tool found two bugs that were not known. The first is the wrong result
of Figure~\ref{fig:motivating}, found by the \texttt{(SELECT e)} expression
rewrite. The second is an assertion failure: \texttt{JSON\_TABLE} does not
assign collations to its context item and \texttt{PASSING} arguments, and a
row comparison over such a value fails an assertion in the executor
(\pg~17, 18 and master). The four-minute smoke run of RQ3 found the second
bug again without help.

Triage of the smoke run also found two false-positive classes in our own
oracles, which we fixed before the campaign. TLP on \texttt{HAVING} dropped the
clause on the unpartitioned side, which turns a single-group aggregate into a
plain query; and \texttt{DISTINCT} over \texttt{numeric} may keep
\texttt{21.0000000000000000} or \texttt{21.00000000000000000000} depending on
the plan, which are equal values. The smoke runs also exposed a harness
error: when another session crashed the server, the crash was blamed on the
test case that happened to be running. \tool now reads the backend process
id from every \texttt{TRAP} and signal line of the log and ignores evidence
from other backends. Over all 18 candidates triaged so far, 3 are real and
13 are false positives or intended changes, all of them from 6 classes that
we fixed; \num{final precision per oracle, before and after fixes}.
