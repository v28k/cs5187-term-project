Hi,

pg_restore_extended_stats() accepts NaN and Infinity in most_common_freqs
and most_common_base_freqs and stores them in the MCV list.
check_mcvlist_array() only checks dimensions, NULLs and length.

CLAMP_PROBABILITY() does not neutralize NaN, so the planner then estimates
the maximum row count for matching clauses. On master (a39e53a7, cassert):

  CREATE TABLE m(a int, b int);
  INSERT INTO m SELECT i%3, i%3 FROM generate_series(1,3000) i;
  CREATE STATISTICS ms (mcv) ON a,b FROM m;
  ANALYZE m;
  SELECT pg_restore_extended_stats(
    'schemaname','public','relname','m',
    'statistics_schemaname','public','statistics_name','ms',
    'inherited', false,
    'most_common_vals','{{0,0},{1,1}}'::text[],
    'most_common_freqs','{NaN,0.3}'::float8[],
    'most_common_base_freqs','{0.1,0.1}'::float8[]);   -- returns t
  EXPLAIN SELECT * FROM m WHERE a=0 AND b=0;           -- rows=1e100

(baseline after ANALYZE is rows=1000). Infinity gives the same result.
Nothing crashes and query results stay correct; as with 7cb9060d and the
attribute-stats thread, this is stored garbage the planner cannot defend
against.

The attached patch rejects non-finite values with a WARNING, like the other
inconsistent inputs in check_mcvlist_array(), and adds tests to stats_import.
Finite but out-of-range values are still accepted, since these functions do
only superficial validation by design.

This only covers the MCV arrays. The float fields inside "exprs" (e.g.
range_empty_frac, null_frac) have the same gap; I left them out to keep this
small and can follow up if there is interest.

make check passes (239/239) with the patch, and stats_import fails without
the C change.
