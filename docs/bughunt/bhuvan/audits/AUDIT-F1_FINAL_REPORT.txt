PostgreSQL Query Optimizer Correctness Bug: NOT IN Null Semantics with
User-Defined Implicit Casts

Local finding ID : AUDIT-F1
Report date      : 2026-10-23 (all times UTC)
Report status    : LOCAL REPORT ONLY. Nothing has been submitted to any
                   PostgreSQL list, tracker, commitfest or maintainer.

Evidence labels used in this report:
  [EXEC]    fact directly demonstrated by execution in this verification
  [SOURCE]  finding supported by reading source code or documentation
  [INTERP]  interpretation or judgement drawn from the facts above
  [UNVERIFIED] claim that was not checked, or could not be checked


===============================================================================
2. EXECUTIVE SUMMARY
===============================================================================

PostgreSQL 19 added a planner transformation (commit 383eb21ebf, 2026-03-12)
that rewrites "x NOT IN (SELECT y ...)" into an anti-join when it can prove
that neither side of the comparison can be NULL. The proof checks the outer
expression, the comparison operator and the sub-select's output column. It
does not check the inner operand that is actually compared. The parser may
wrap the sub-select's output in an implicit cast, and a cast function is
allowed to return NULL for a non-NULL input. When that happens the comparison
is NULL, so NOT IN is NULL and the row must not qualify. The anti-join instead
treats the comparison as "no match" and returns the row.

Verified in this session on freshly built, isolated clusters:

  * [EXEC] The original reproducer runs as written, without errors, on all
    five builds.
  * [EXEC] On 19rc1 (exact tag REL_19_RC1), the REL_19_STABLE tip and master
    896246ea, the reproducer returns 1 row instead of 0, in 3 of 3 runs each.
    The plan is an anti-join (hash, merge or nested loop).
  * [EXEC] On 18.6 (exact tag REL_18_6) it returns 0 rows in 3 of 3 runs,
    using a hashed SubPlan.
  * [EXEC] On the same affected build, the identical predicate gives the
    correct 0 rows whenever the transformation is prevented (control queries).
    PostgreSQL's own evaluation of the NOT IN expression gives NULL on every
    version.
  * [EXEC] An unprivileged role can trigger it with a type it owns. The
    verbatim reproducer, which casts int to text, needs a superuser.
  * [EXEC] The proposed fix (41 lines in subselect.c) makes every tested
    variant correct. With the fix plus a new regression test:
      - core suite: 239/239 pass;
      - isolation suite: 134/134 pass;
      - contrib suites: 191 test lines, 0 failures.
    Without the fix, the new regression test fails for exactly the intended
    reason.
  * [EXEC] The fix has a cost. It also gives up the anti-join for queries
    whose sub-select side needs a built-in non-binary cast, for example
    "numeric_col NOT IN (SELECT int_col ...)". Those return to PostgreSQL 18
    behaviour (hashed SubPlan). Results stay correct.

Final status: A. CONFIRMED REPRODUCIBLE BUG (see Section 3).

5. BUG DESCRIPTION
===============================================================================

When a WHERE clause contains "expr NOT IN (subquery)" at top level, the
planner calls convert_ANY_sublink_to_join() with under_not = true
(prepjointree.c lines 1004-1016). Since 383eb21ebf, that function produces a
JOIN_ANTI if two checks pass (subselect.c lines 1383-1385):

  * sublink_testexpr_is_not_nullable() returns true. It checks that every
    operator belongs to a btree or hash opfamily and that every OUTER
    operand is provably non-nullable.
  * query_outputs_are_not_nullable() returns true. It checks that every
    output column of the sub-select is provably non-nullable.

Neither check looks at the INNER operand of the comparison as the parser
built it. In the reproducer the test expression is

    o.t = i2t($1)    with $1 a PARAM_SUBLINK for s.i

and i2t(0) is NULL. Because s.i is NOT NULL, query_outputs_are_not_nullable()
succeeds. Because o.t is NOT NULL and "=" (texteq) is a btree member,
sublink_testexpr_is_not_nullable() succeeds. The planner therefore assumes
the comparison can never be NULL, which is false.

Observable effect: rows that NOT IN must reject (its value is NULL) are
returned by the anti-join. The effect requires all of the following:
  - both sides provably non-nullable (otherwise no conversion);
  - an implicit cast on the sub-select side chosen by operator resolution;
  - that cast returning NULL for a non-NULL value present in the sub-select.

6. EXPECTED SQL SEMANTICS
===============================================================================

[SOURCE] PostgreSQL documentation (master tree 896246ea):

  * doc/src/sgml/func/func-subquery.sgml, lines 162-164:
      "The result of NOT IN is 'true' if only unequal subquery rows are
       found ... The result is 'false' if any equal row is found."
  * Same file, lines 168-172: the result "will be null, not true",
    "in accordance with SQL's normal rules for Boolean combinations of null
    values".
  * Same file, lines 141-147: per-row results are combined by the normal
    Boolean rules; if they are "either unequal or null, with at least one
    null", IN is null.
  * doc/src/sgml/ref/select.sgml, lines 786-789: in WHERE, "A row satisfies
    the condition if it returns true".

Applied to the reproducer (o = {'1'}, s = {0}, i2t(0) = NULL):

  '1' = i2t(0)             ->  '1' = NULL  ->  NULL (neither equal nor unequal)
  '1' NOT IN (that set)    ->  NOT (NULL)  ->  NULL
  WHERE NULL               ->  row does not qualify
  Expected result of "SELECT t FROM o WHERE t NOT IN (SELECT i FROM s)": 0 rows

Contrast: NOT EXISTS (SELECT 1 FROM s WHERE o.t = s.i) is TRUE here, because
NOT EXISTS only asks whether a TRUE match exists. An anti-join implements
NOT EXISTS semantics, which is why the conversion is only valid when no
comparison can be NULL.

[EXEC] Explicit inspection queries (script v1, all five builds, identical):

  [S1] pg_cast entry after CREATE CAST:
       integer | text | i2t(integer) | castcontext i | castmethod f
  [S2] i2t(0) = <NULL>, i2t(0) IS NULL = t, i2t(1) = '1'
  [S3] SELECT o.t, s.i, (o.t = s.i), (o.t = s.i) IS NULL FROM o, s
       -> 1 | 0 | <NULL> | t
  [S4] Stored parse tree of the view "SELECT t FROM o WHERE t NOT IN
       (SELECT i FROM s)":
       {FUNCEXPR :funcid <oid of i2t> ... :funcformat 2 ...
        :args ({PARAM :paramkind 2 :paramid 1 ...
       funcformat 2 = COERCE_IMPLICIT_CAST and paramkind 2 = PARAM_SUBLINK
       (src/include/nodes/primnodes.h lines 389-392 and 761-764).
       So the implicit cast i2t() is applied to the sub-select output inside
       the comparison.
  [S5] ('1' = NULL) -> NULL; ('1' NOT IN (NULL)) -> NULL;
       rows qualifying under WHERE NULL -> 0
  [S6] NOT EXISTS (...) -> t ;  NOT IN (...) -> <NULL>

[INTERP] This rules out a faulty assumption about coercion or expression
semantics. The cast is applied where claimed, it returns NULL as claimed, and
PostgreSQL's own expression evaluation gives NULL for the NOT IN.

7. MINIMAL REPRODUCER
===============================================================================

The original reproducer was run verbatim, unchanged, in a fresh database:

  CREATE FUNCTION i2t(int) RETURNS text
  IMMUTABLE STRICT LANGUAGE sql
  AS $$ SELECT CASE WHEN $1 <> 0 THEN format('%s', $1) END $$;

  CREATE CAST (int AS text)
  WITH FUNCTION i2t(int) AS IMPLICIT;

  CREATE TABLE o (t text NOT NULL);
  INSERT INTO o VALUES ('1');

  CREATE TABLE s (i int NOT NULL);
  INSERT INTO s VALUES (0);

  SELECT t, t NOT IN (SELECT i FROM s) AS not_in FROM o;

  SELECT t FROM o WHERE t NOT IN (SELECT i FROM s);

Validity checks [EXEC, all five builds]:
  * Before CREATE CAST, pg_cast has 0 rows with source int4 and target text,
    so the cast neither conflicts with nor replaces an existing cast.
  * Every statement succeeded; psql exit code 0; no ERROR lines.
  * The verbatim SQL requires a superuser, because int and text are built-in
    types (CREATE CAST requires owning the source or target type:
    create_cast.sgml lines 165-166). The verification ran as the bootstrap
    superuser "postgres".

Unprivileged variant (script v5b). This is an addition, not a replacement for
the original. It runs as a NOSUPERUSER role that owns an enum type:

  CREATE TYPE level AS ENUM ('low', 'high');
  CREATE FUNCTION level_to_text(level) RETURNS text IMMUTABLE STRICT
    LANGUAGE sql
    AS $$ SELECT CASE WHEN enum_eq($1, 'high'::level) THEN 'high'::text END $$;
  CREATE CAST (level AS text) WITH FUNCTION level_to_text(level) AS IMPLICIT;
  CREATE TABLE lo (t text NOT NULL);  INSERT INTO lo VALUES ('x');
  CREATE TABLE li (l level NOT NULL); INSERT INTO li VALUES ('low');
  SELECT t FROM lo WHERE t NOT IN (SELECT l FROM li);   -- correct: 0 rows

Changes needed to reach this variant, all documented in the logs:
  * Attempt 1 (script v5) cast int to the enum. It failed on every build with
    "operator does not exist: level = integer", because enum equality is the
    polymorphic anyenum = anyenum. That attempt was abandoned.
  * In attempt 2 the function body first used "$1 = 'high'". After the
    implicit level->text cast existed, this recursed (stack depth exceeded)
    and then became ambiguous ("operator is not unique: level = level").
    Calling enum_eq() directly avoids operator resolution. These are side
    effects of creating a cross-category implicit cast, not part of the bug.
  * Each v5b log contains one "ERROR: role "f1_user" already exists". The
    role is cluster-wide and was created by script v5. The query
    "SELECT ... rolsuper" in each run shows is_superuser = f.

11. ROOT CAUSE IN THE SOURCE CODE
===============================================================================

All line numbers refer to the unmodified master tree at 896246ea.

[SOURCE] Parser: how the inner operand is built

  * src/backend/parser/parse_expr.c, transformSubLink():
      lines 1964-1986 build one PARAM_SUBLINK Param per sub-select output
      column; lines 2008-2012 call make_row_comparison_op() with those
      Params as the right-hand list.
  * parse_expr.c, make_row_comparison_op() (line 2839):
      - line 2882: make_op() is called for each column pair;
      - lines 2910-2911: a single column yields one OpExpr;
      - lines 2970-2973: "=" or "<>" yield an AND/OR of OpExprs;
      - lines 3009-3030: other operators yield a RowCompareExpr. The comment
        at 3009-3010 notes that "make_op inserted coercion operations" may be
        present in largs/rargs.
  * src/backend/parser/parse_oper.c, make_op() (line 711):
      - line 771: args = list_make2(ltree, rtree), so the outer side is
        first and the Param second;
      - line 813: make_fn_arguments() coerces both arguments in place to the
        operator's declared input types. That is where i2t() wraps the Param.

[SOURCE] Planner: the conversion and its checks

  * src/backend/optimizer/prep/prepjointree.c, lines 1004-1016: for
    NOT (ANY sublink) in a top-level qual, convert_ANY_sublink_to_join() is
    called with under_not = true.
  * src/backend/optimizer/plan/subselect.c, convert_ANY_sublink_to_join()
    (line 1356). Lines 1383-1385:
        if (under_not &&
            (!sublink_testexpr_is_not_nullable(root, sublink) ||
             !query_outputs_are_not_nullable(subselect)))
            return NULL;
    Line 1459 builds the join quals with convert_testexpr(). Line 1465 sets
    jointype = JOIN_ANTI.
  * subselect.c, sublink_testexpr_is_not_nullable() (line 1501):
      - OpExpr branch: line 1524 checks op_is_safe_index_member(); line 1527
        collects only linitial(opexpr->args), the outer side.
      - AND/OR branch: lines 1544 and 1547, same pattern.
      - RowCompareExpr branch: line 1562 collects only rcexpr->largs.
      - Line 1589: each collected outer expression must pass
        expr_is_nonnullable(..., NOTNULL_SOURCE_HASHTABLE).
    The function never inspects lsecond(opexpr->args) or rcexpr->rargs. The
    function as introduced in 383eb21ebf has the same structure (verified
    with git show).
  * src/backend/optimizer/util/clauses.c, query_outputs_are_not_nullable()
    (line 2177): examines the sub-select's targetList entries (stripping
    RelabelType at line 2225; expr_is_nonnullable(..., CATALOG) at line
    2265). It sees s.i, which is NOT NULL, not i2t(s.i).

[SOURCE] Why the missed check matters

  The commit message of 383eb21ebf states the safety condition: the result
  is identical when "neither side of the comparison can yield NULL" and the
  operator cannot return NULL for non-null inputs. The compared right-hand
  value is i2t($1), not $1. Nothing in PostgreSQL forbids a cast function
  from returning NULL for a non-NULL input:
    - doc/src/sgml/ref/create_cast.sgml contains no statement about NULL
      results;
    - the executor simply propagates the function's NULL result, as S2 and
      S3 show.

[SOURCE] Related facts used in the patch review

  * Input functions cannot return NULL for a non-NULL string:
      - fmgr.c lines 1551-1563 (InputFunctionCall raises an error);
      - execExprInterp.c lines 1412-1437 (EEOP_IOCOERCE never sets resnull
        from the input function; the check there is an Assert).
  * Domain coercion only raises errors: execExprInterp.c lines 4484-4509.

Test SQL, exactly as added (41 lines):

  -- No ANTI JOIN: the sub-select's output is coerced to the operator's input
  -- type by a cast function, which can return NULL for a non-null input, so a
  -- comparison can yield NULL even though both sides are non-nullable
  CREATE FUNCTION int4_to_text_nullzero(int4) RETURNS text
      AS $$ SELECT CASE WHEN $1 <> 0 THEN format('%s', $1) END $$
      LANGUAGE sql IMMUTABLE STRICT;
  CREATE CAST (int4 AS text) WITH FUNCTION int4_to_text_nullzero(int4) AS IMPLICIT;
  CREATE TEMP TABLE nn_text_tab (t text NOT NULL, k int NOT NULL);
  CREATE TEMP TABLE nn_int_tab (i int NOT NULL, k int NOT NULL);
  INSERT INTO nn_text_tab VALUES ('1', 1), ('5', 1);
  INSERT INTO nn_int_tab VALUES (0, 1), (1, 1);

  EXPLAIN (COSTS OFF)
  SELECT * FROM nn_text_tab WHERE t NOT IN (SELECT i FROM nn_int_tab);

  -- '1' matches 1, and '5' is compared with the NULL that 0 is cast to, so no
  -- row qualifies
  SELECT * FROM nn_text_tab WHERE t NOT IN (SELECT i FROM nn_int_tab);

  -- The cast cannot return NULL here, so '5' qualifies but '1' does not
  SELECT * FROM nn_text_tab WHERE t NOT IN (SELECT i FROM nn_int_tab WHERE i <> 0);

  -- Likewise for the multi-column form
  EXPLAIN (COSTS OFF)
  SELECT * FROM nn_text_tab WHERE (t, k) NOT IN (SELECT i, k FROM nn_int_tab);

  SELECT * FROM nn_text_tab WHERE (t, k) NOT IN (SELECT i, k FROM nn_int_tab);

  -- Likewise for a row comparison
  EXPLAIN (COSTS OFF)
  SELECT * FROM nn_text_tab WHERE NOT (t, k) > ANY (SELECT i, k FROM nn_int_tab);

  SELECT * FROM nn_text_tab WHERE NOT (t, k) > ANY (SELECT i, k FROM nn_int_tab);

  -- ANTI JOIN: a binary-compatible relabeling of the sub-select's output cannot
  -- produce NULLs
  CREATE TEMP TABLE nn_varchar_tab (v varchar NOT NULL);

  EXPLAIN (COSTS OFF)
  SELECT * FROM nn_text_tab WHERE t NOT IN (SELECT v FROM nn_varchar_tab);

Core of the change:

  static bool
  sublink_inner_arg_is_param(Node *arg)
  {
      while (arg && IsA(arg, RelabelType))
          arg = (Node *) ((RelabelType *) arg)->arg;

      return arg && IsA(arg, Param) &&
          ((Param *) arg)->paramkind == PARAM_SUBLINK;
  }

  /* in each branch, next to the existing op_is_safe_index_member() check */
  if (!sublink_inner_arg_is_param(lsecond(opexpr->args)))
      return false;
  ...
  foreach_ptr(Node, rarg, rcexpr->rargs)
  {
      if (!sublink_inner_arg_is_param(rarg))
          return false;
  }

14. PATCH REVIEW AND LIMITATIONS
===============================================================================

Does it fix the root cause?
  [SOURCE + EXEC] Yes. The missing proof obligation is the nullability of
  the inner compared operand. The fix adds that check in all three
  test-expression shapes the parser can produce (Section 11). All tested
  variants become correct: single, multi-column, correlated, row comparison
  and the unprivileged-role variant.

Is it conservative (can it break SQL semantics)?
  [SOURCE] The patch only adds "return false" paths before the conversion
  happens. It can only prevent anti-joins that the unpatched code would have
  formed, never create new ones. The fallback is the pre-19 hashed or plain
  SubPlan evaluation, whose semantics are the reference used in this report.
  [INTERP] It cannot introduce false positives (unsafe conversions). It can
  only add false negatives (missed conversions).

Parser-generated forms:
  * RelabelType: accepted, because binary relabeling cannot turn a value into
    NULL. [EXEC] text NOT IN (SELECT varchar) and int NOT IN (SELECT domain
    over int) keep the anti-join.
  * PARAM_SUBLINK: required. At this stage (before convert_testexpr, line
    1459) the inner operands are PARAM_SUBLINK Params (verified in S4). A
    correlated sub-select changes only which relations are referenced, not
    the test expression shape. [EXEC] The correlated variant is fixed.
  * Cross-type operators (int8 = int4, int4 = int8, timestamptz = date): no
    coercion is inserted, so the anti-join is kept. [EXEC]
  * Outer side: unchanged. A coercion there was already rejected by
    expr_is_nonnullable(). [EXEC] int4 NOT IN (SELECT numeric) uses a SubPlan
    on both builds.

Unnecessary loss of optimization (false negatives):
  [EXEC] Script v3, plan shape on baseline vs patched:
    int4 NOT IN int4      (no coercion)          anti-join | anti-join
    int8 NOT IN int4      (cross-type operator)  anti-join | anti-join
    int4 NOT IN int8      (cross-type operator)  anti-join | anti-join
    text NOT IN varchar   (RelabelType)          anti-join | anti-join
    int4 NOT IN domain    (RelabelType)          anti-join | anti-join
    timestamptz NOT IN date (cross-type op)      anti-join | anti-join
    numeric NOT IN int4   (int4->numeric cast)   anti-join | SubPlan  <- lost
    float8 NOT IN int4    (int4->float8 cast)    anti-join | SubPlan  <- lost
    int4 NOT IN numeric   (outer-side cast)      SubPlan   | SubPlan
  [EXEC] Master and 19rc1 have 69 implicit casts implemented by functions,
  all strict functions in language "internal" (18.6: 65). They also have 3
  implicit I/O casts and 53 implicit binary casts.
  [UNVERIFIED] Whether every one of those 69 C functions never returns NULL
  for non-NULL input was not audited function by function.
  [SOURCE] I/O coercion (CoerceViaIO) and domain coercion (CoerceToDomain)
  cannot turn a non-NULL value into NULL (Section 11), yet the patch rejects
  them too. ArrayCoerceExpr never yields a NULL array from a non-NULL array.
  [INTERP] These are performance regressions relative to 19rc1, not to any
  released version: 18.x never converted NOT IN at all. Possible refinements
  for maintainers to decide:
    (a) also accept CoerceViaIO, CoerceToDomain and ArrayCoerceExpr;
    (b) also accept implicit casts whose function is a known built-in;
    (c) keep the simple conservative rule.
  Relevant precedent [SOURCE, pgsql-hackers thread "Teach expr_is_nonnullable()
  to handle more expression types", Oct 2026]: for a similar case, Robert Haas
  preferred not to add catalog lookups to nullability checks, and Richard Guo
  chose the simple conservative removal (commit f5635c2786).

Coding conventions:
  [SOURCE] The patch follows the surrounding conventions:
    - a static prototype in the existing prototype list;
    - a block comment before the helper;
    - foreach_ptr as used nearby;
    - IsA()/castNode-style checks;
    - comment style matching the existing header.
  pgindent was not run. [UNVERIFIED] whitespace/pgindent conformance.

Interaction with an open patch:
  [SOURCE] An open pgsql-hackers thread ("Prove a NOT IN's left-hand
  expressions non-nullable from quals", Jun-Aug 2026, v2 posted) changes the
  signature of sublink_testexpr_is_not_nullable(). If that lands first, this
  fix will need a trivial rebase. It does not address the inner operand.

Overall assessment [INTERP]:
  Correct and safe for the bug. The open question is whether maintainers
  accept the optimization loss for built-in non-binary casts or prefer
  refinement (a) or (b). The patch should be presented as a proposal with
  this trade-off stated.

18. IMPACT, PRECONDITIONS, AND SEVERITY ASSESSMENT
===============================================================================

Impact [EXEC]: silent wrong query results. Rows are returned that NOT IN
semantics exclude. No error, crash, assertion failure, data modification or
corruption was observed.

Preconditions (all required) [EXEC + SOURCE]:
  1. PostgreSQL 19 or master; 18.6 and earlier are unaffected.
  2. "expr NOT IN (subquery)", or NOT (row op ANY (subquery)), as a
     top-level qual, so that the transformation fires.
  3. Both the outer expression and the sub-select output column provably
     non-nullable, e.g. through NOT NULL constraints.
  4. Operator resolution applies an implicit cast to the sub-select side,
     which needs a type mismatch with no direct operator.
  5. That implicit cast returns NULL for a non-NULL value that actually
     occurs in the sub-select.

Precondition 5 is the decisive one, and it is unusual:
  * [EXEC] None of the built-in implicit casts in the tested builds is a
    plausible trigger. All 69 function-based ones are strict internal C
    functions.
    [UNVERIFIED] No function-by-function audit was done.
  * [SOURCE] create_cast.sgml lines 138-149 recommends implicit casts only
    for "information-preserving transformations" within a type category, and
    calls cross-category casts such as text/int4 "best made explicit-only".
    The reproducer's cast goes against this advice, though PostgreSQL accepts
    it.
  * [EXEC] No superuser is needed if the user owns the source or target type
    (v5b).

[INTERP] Practical likelihood: low. A user must deliberately create an
implicit cast that maps a non-NULL value to NULL. Extensions that define such
casts would also be affected; none was examined.

Severity [INTERP]: low to moderate. It is a genuine correctness violation
(wrong results without any error) in a release-candidate feature. It is
narrow in practice because of precondition 5. Maintainers have treated a
comparable "rare in practice, but nothing forbids it" case as a bug worth
fixing (f5635c2786).

Security: not classified as a security vulnerability. No evidence of
privilege escalation, data disclosure or memory unsafety was found or
sought. Any security relevance would need separate analysis.
