# 0. The short version

* **Goal of the project:** find a new bug in PostgreSQL by fuzzing (automatically generating
  many SQL queries and checking the server's answers), report it to the PostgreSQL
  developers, and send a fix. The older document `bughunt/HANDOFF.md` describes
  session 1. This file covers session 2 only.
* **BUG-01** (JSON_TABLE collation bug, found in session 1) was already filed by Venu as
  **BUG #19768** with the patch. This session confirmed there is no duplicate, rebased the
  patch onto current master, and re-ran the full test suite: **239/239 pass**. It is waiting
  for a reply from a PostgreSQL committer.
* **Candidate 2** (crash recovery fails with "File exists") now **reproduces every time**, but it
  is a **known bug, #17731** (reported 2022). Not new, not filed.
* The **6-hour grammar hunt** ran on 17 Oct (319,901 test cases over 2 trials). It found 3 crash
  signatures. All 3 are **one known bug, #19766** (reported one day earlier by someone else).
  Not new. A reply to that thread is **drafted, not sent** (`reply-19766-draft.txt`).
* **New this session:** a second kind of checker, the **metamorphic fuzzer** (TLP + NoREC),
  plus 53 hand-written probes for the areas the plan said to test next. No new bug yet.
* **Running now:** 3 endless fuzzing loops (section 6). None has found anything so far.
* **Nothing was sent upstream this session.** Everything sent so far was sent by the team itself.

# 1. Words used in this document

| Word | Meaning |
|---|---|
| master | The newest PostgreSQL development code (it will become version 20). |
| 18.6 | The current released PostgreSQL version. We use it as a "reference" to compare with. |
| assert build / cassert | PostgreSQL built with `--enable-cassert`. Internal sanity checks are on; when one fails the server prints `TRAP: failed Assert(...)` and that backend crashes. Many bugs show up only this way. |
| backend | The server process that serves one client connection. |
| fuzzer | A program that generates many random SQL queries and runs them. |
| oracle | The rule that decides "this answer is wrong" or "this is a bug" (crash, assertion, wrong rows, ...). |
| signature | A short hash (e.g. `d6056a3966f1`) of a failure's stack trace. Same signature means the same crash location. |
| differential testing | Run the same query two ways (two versions, or two planner settings) and compare the rows. Different rows means one of them is wrong. |
| TLP | Ternary Logic Partitioning. The rows of `Q` must equal the rows of `Q WHERE p` + `Q WHERE NOT p` + `Q WHERE p IS NULL`. |
| NoREC | `SELECT count(*) ... WHERE p` must equal `SELECT sum(CASE WHEN p THEN 1 ELSE 0 END) ...`. The second form stops the planner from using `p` to skip rows. |
| planner settings / GUCs | Options like `enable_hashjoin = off` or `debug_parallel_query = on`. They change *how* a query runs, never *what* it returns. |
| pgsql-bugs | The PostgreSQL bug mailing list. PostgreSQL takes bug reports and patches by email, not by GitHub pull request. |

## 2.3 The three fuzzers and what each one checks

```text
                 +--------------------------+
 grammar         |  pgfuzz (src/pgfuzz/)    |  typed SQL grammar -> test cases -> server
 hunt  --------> |  oracles: crash, TRAP,   |  each statement also re-run under 2 random
 (finished)      |  internal error, and     |  planner settings; different rows = wrong result
                 |  plan-variant diff       |
                 +--------------------------+

                 +--------------------------+        +-----------------+
 joinfuzz2 ----> |  same random join/agg    | -----> | master (5434)   |  random planner settings
 (running)       |  query sent to BOTH      | -----> | 18.6   (5435)   |  plain settings
                 +--------------------------+        +-----------------+
                   different rows, or an error/crash on one side only = candidate

                 +--------------------------+        +-----------------+
 metafuzz -----> |  one query in 2 forms    | -----> | master (5432 or |
 (running, NEW)  |  that must be equal      |        |  5433)          |
                 |  (TLP or NoREC)          |        +-----------------+
                 +--------------------------+
                   the 2 forms disagree = wrong result (works even if 18.6 has the same bug)
```

* **Grammar hunt** (`python -m pgfuzz run configs/cloud_hunt.yaml`): the team's main tool. It
  finds crashes and assertion failures over the whole SQL language.
* **joinfuzz2** (`src/xversion/joinfuzz2.py`, written in session 1): finds results that
  *changed* between 18.6 and master (regressions). Blind to bugs that both versions have.
* **metafuzz** (`src/xversion/metafuzz.py`, **written this session**): finds wrong results inside
  one server, so it also sees bugs that 18.6 shares. It reuses joinfuzz2's query generator,
  tables (schema `jf2`) and random planner settings.

# 5. Bugs: what was found and what the verdict is

## 5.1 BUG-01 = BUG #19768 (ours, filed, waiting for review)

* **What:** `JSON_TABLE` does not assign collations to its context item and `PASSING`
  arguments. On 18.6, `ROW(1,2) < ROW(3,4)` inside JSON_TABLE returns **false** (wrong result),
  and text comparisons fail with "could not determine which collation". On assert builds the
  backend crashes.
* **Fix:** one line in `src/backend/parser/parse_jsontable.c`:
  `assign_expr_collations(pstate, tf->docexpr);` plus regression tests.
* **Filed by** Venu Kummari on 2026-10-16, with the patch:
  <https://www.postgresql.org/message-id/flat/19768-3633daa830be95db@postgresql.org>
* **This session:** no duplicate found; patch rebased on master 7787aec; `make check` 239/239.
  The probes also showed 18.6 giving wrong answers through 3 more shapes (NESTED PATH, FORMAT
  JSON, LATERAL), and the patch fixes all of them.
* **Status:** 2 messages in the thread (both ours), **no committer reply yet**.

## 5.2 Candidate 2 = known BUG #17731 (not new, not filed)

* **What:** after a crash, restart fails with
  `FATAL: could not create file "base/5/16384": File exists`.
* **Reproducer** (`scripts/cand2_repro.py`): CHECKPOINT; session 1 runs
  `BEGIN; CREATE UNLOGGED SEQUENCE ...` (or a table); session 2 commits anything (this flushes
  the WAL); session 1 rolls back; `pg_ctl stop -m immediate`; `pg_ctl start`.

| Build | rollback (savepoint or top level), sequence or table | transaction left open (control) |
|---|---|---|
| master (old `install/master` build, cassert) | **fails** in every run (sequence and table, savepoint and top-level rollback; 4 repeats of the sequence case) | recovers |
| master 7787aec + BUG-01 patch | **fails** | not run |
| 18.6 | **fails** in all 4 combinations | recovers |

A second `pg_ctl start` recovers.
* **Why:** after the rollback only an empty main file is left on disk. Recovery re-creates the
  "init fork" from the WAL, then tries to copy it onto the main file with "create only if new",
  and the old file is still there.
* **Known as** BUG #17731 (2022, PostgreSQL 15.1):
  <https://www.postgresql.org/message-id/17731-85ab9766c4257f8f@postgresql.org>. The developers
  said the real fix is too big to back-patch. No fix commit.

## 5.3 Grammar hunt results = known BUG #19766 (not new)

Hunt: 17 Oct 13:12 to 19:14 UTC, 2 trials x 6 hours, patched master.

| Trial | Test cases | Valid queries | Bug candidates |
|---|---|---|---|
| 0 | 180,130 | 99.17% | 3 |
| 1 | 139,771 | 99.67% | 0 |

The 3 candidates (`d6056a3966f1`, `a612860ff94b`, `41601cda1d7c`, in
`src/results/cloud_hunt/grammar/trial-00/failures/`) are one bug:
`TRAP: failed Assert("toc->toc_entry[i].key != key"), File: "shm_toc.c", Line: 190`
during `EXPLAIN ANALYZE` of a parallel plan. Each was replayed alone on a fresh cluster:

| Settings | master 7787aec | 18.6 |
|---|---|---|
| default | ok | ok |
| forced parallel | **crash** (Material / Agg) | ok |
| parallel + `cpu_tuple_cost 10` | **crash** (Sort) | ok |
| `work_mem 64kB` + `cpu_tuple_cost 10`, no forced parallel | **crash** (Sort) | ok |
| plain `EXPLAIN` or plain `SELECT` | ok | ok |

* **Why:** a Parallel Append has several children (partitions, or an inheritance parent and child)
  whose filters share **one** subquery. The parallel setup code visits that subquery once per
  child and registers the same ID twice, which fails the assertion. 18.6 is fine because the
  assertion exists only on master (commit 43222b8e53f).
* **Known as** BUG #19766, reported 2026-10-16 15:24 UTC by Alperen Keles:
  <https://www.postgresql.org/message-id/19766-c3d105a4e0ec5487@postgresql.org>. Same assertion,
  same explanation, same three functions. No reply or fix yet.
* **What we can add:** it also happens with an **inheritance** parent and child (not only
  partitions), with a 4-line reproducer (`scripts/repro_19766_inherit.sql`). On master it crashes
  for all 3 of the report's queries; 18.6 is fine. The reply is drafted (section 7).

## 6.4 If a candidate shows up

1. Open the saved `.sql` file; it has the settings and the query (or both TLP/NoREC queries).
2. Replay it on a **throwaway** cluster (`scripts/run_probe.sh BIN PORT /tmp/x file.sql`), on
   both `install/bug01` and `install/REL_18_STABLE`.
3. Rule out our own false positives first: e.g. `ARRAY(SELECT ...)` without `ORDER BY`, float
   rounding, `LIMIT` without `ORDER BY`, volatile functions.
4. Shrink the query by hand until it is a few lines.
5. **Search the archive** (postgresql.org/search, pgsql-bugs and pgsql-hackers) before
   believing it is new. In this session both new leads (candidate 2 and the grammar-hunt
   crash) turned out to be already reported by other people.
6. Write it up in `bughunt/LOG.md` with the exact runs.
